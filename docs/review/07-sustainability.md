# 축 8 — 지속가능성 (번들 · 테스트 · 생성물 · 운영)

## 요약 (3줄)
- 번들 예산 여유와 생성물 체계는 생각보다 튼튼하다. `arsenal.json` 은 `balance --check` 가 이미 잡고, 번들은 최근 3주 동안 거의 늘지 않았다(+16KB).
- 1년 안에 사람을 다치게 할 것은 세 가지다. 테스트 하드 워치독(직렬 실행이 완주하지 못함), 리플레이가 버그 재현 도구로 쓸 수 없는 형태라는 점, 최상위 이름 충돌을 잡는 검사가 없다는 점.
- 락파일 부재는 실제 위험이지만 작다. 캐럿이 25.x 안에 갇혀 있고 영향이 CI 에 한정된다.

## 측정값
**번들 예산 (실측, `node tools/validate.js`)**
- R20: `content.js` 1193.6 KB / 1600 KB (75% 사용, 406.4 KB 남음). `content.css` 81.0 KB / 200 KB (40%).
- 성장률(실측, `git ls-tree` 로 src/ 크기): 10-02 395KB → 10-14 745KB → 10-15 1113KB → 11-04 1222KB. 10-15 이후 3주 동안 +16KB. 폭증은 무기 아트(`44-weapon-art.js` 101KB)와 무기 확장 때였고 지금은 평탄하다. 이 속도면 남은 406KB 는 수개월 이상이다. 무기 4종 추가 단계(9단계)가 한 번 더 오면 100~200KB 를 쓸 수 있으니 "1~2단계 분량"이 안전한 어림이다.
- 주입 비용: `manifest.json` 에 `content_scripts` 가 없고 권한이 `activeTab` + `scripting` + `storage` 뿐이다. 즉 **사용자가 켠 탭에만 주입**되고 모든 페이지 로드에 붙지 않는다. Node(v24.12) `vm.Script` 로 1.19MB 를 컴파일하면 7.0~7.7 ms(전처리 파싱만, 7회 반복). 즉 파싱은 문제가 아니다. 실행 시점 초기화 비용과 Chrome 느린 기기 수치는 **측정하지 못했다**(추정 불가).

**블록별 테스트 시간 (부분 실측)**
- `CRS_LANES=1 node test/e2e.js` 를 백그라운드로 돌렸다. 하드 워치독이 240+20 초에 프로세스를 죽여 `ammo`, `rules`, `core` 까지만 나왔다. 직렬이라 시간은 누적: ammo 109.1 s, rules 185.8 s(차 ≈ 77 s), core 255.3 s(차 ≈ 69 s). 부하 평균 약 7.3 인 머신이다.
- 나머지 블록(combat, depth, debris, settings, roles, 스위트 B·C·D)은 **측정하지 못했다.** `test/e2e.js:14192-14204` 의 주석값(55, 43, 37, 17, 6, D 20 s)으로 추정했다. 큐 순서는 ammo 109 > rules 77 > core 69 로 실측과 주석이 맞는다. 순서는 아직 유효하다.
- 추정 합(직렬): 약 440 s + B·C. CI 3레인이면 이상적으로 150~170 s 로 추정(실측 아님. ci.yml 주석의 "1분 47초"는 오래된 값).

## 발견 (심각도 순)

### 1. 테스트 하드 워치독이 직렬 실행을 죽인다 — 심각도 중 · 비용 소
**증거**: `test/e2e.js:343` `TIME_BUDGET_MS = 240000`, `:14119` 에서 `TIME_BUDGET_MS + 20000` 뒤 강제 종료. 위 실측: `CRS_LANES=1` 이 255 s 에서 `FAIL runtime budget exceeded (240 s)` / `SUMMARY: 776 passed, 1 failed (timeout)` 로 끝남(1256 중 776만 실행).
**무엇이 문제인가**: 메모리 규칙("머신이 바쁘면 CRS_LANES=1")과 코드가 충돌한다. 바쁜 머신에서 직렬로 돌리면 완주할 수 없고, 어떤 단언이 실패했는지가 아니라 시간 초과가 보고된다. "완료 판정은 항상 전체 실행"이라는 CLAUDE.md 규칙을 지킬 방법이 부하 높은 날엔 없다.
**언제 터지는가**: 지금 이미. 그리고 CI 에서는 스위트 합이 늘면 터진다. 합이 440→약 700 s(블록 1.6배)면 3레인 ≈ 240 s 가 되어 CI 도 빨갛게 변한다. 1년 뒤 스위트가 2배가 되는 것은 현재 속도(한 달에 116 s)로 충분히 가능하다.
**제안**: `CRS_LANES` 가 지정되면 예산을 레인 수에 비례해 늘리거나, 워치독을 "총시간"이 아니라 "블록별 진척 없음"으로 바꾼다. CI 쪽은 예산 240 s 를 실측값에 맞춰 두되 `ammo` 단독 시간(109 s)이 하한임을 문서화한다.
**반대 심문**: 예산이 있는 이유가 폭주 감지이므로 환경변수 `CRS_TIME_BUDGET_MS` 로 이미 우회 가능하다. 아는 사람에게는 문제가 아니다. 다만 메모리의 지침만 따르면 걸린다.

### 2. 리플레이는 사용자 버그를 재현할 수 있는 형태가 아니다 — 심각도 중 · 비용 중
**증거**: `src/98-inspect.js:365` 내보내기 형식은 `{v, startedAt, viewport:{w,h}, ops}` 뿐이다. URL, DOM 지문, 스크롤 위치, 설정 스냅샷이 없다. `.github/ISSUE_TEMPLATE/bug_report.yml` 필드는 what-happened, steps, version, chrome, os, install, console, extra 이고 사이트 URL 도 리플레이도 묻지 않는다. 내보내기는 옵션 페이지(`options/options.html:96`)에만 있다. `recordReplay` 기본값은 `true` (`settings-schema.json:27`).
**무엇이 문제인가**: "A 사이트에서 깨졌어요"에 대해 좌표 목록(2000개 상한)만 받는다. 같은 페이지의 같은 DOM 이 아니면 같은 요소가 맞지 않는다. 사이트는 바뀌고 로그인 뒤 화면은 재현이 안 된다. 리플레이는 "내 플레이 공유"로 설계됐지 진단 번들이 아니다.
**언제 터지는가**: 출시 후 첫 번째 "특정 사이트에서만 안 돼요" 리포트. 필터 규칙(CSP, Trusted Types, 셰도 DOM, iframe) 문제는 사이트마다 달라서 가장 흔한 리포트 유형이다.
**제안**: 옵션 페이지에 "진단 복사" 버튼을 둔다(버전, 설정, URL 의 origin 만, `stats().lastError`, 최근 N 개 오류, 리플레이 첨부). 버그 템플릿에 "어느 사이트(origin)에서" 필드를 필수로 추가한다. 개인정보라 URL 은 origin 까지만 쓴다.
**반대 심문**: 개인 재미 프로젝트라면 소수 리포트를 수동으로 물어보면 된다. 또 DOM 지문을 넣으면 개인정보 문제가 생긴다. 수동 응답이 감당되는 규모면 비용 대비 효과가 낮다. 웹스토어 출시가 목표이므로 일단 중으로 둔다.

### 3. 최상위 이름 충돌을 잡는 검사가 없다 — 심각도 중 · 비용 소
**증거**: `grep -n "duplicate\|collision" tools/build.js tools/validate.js` 가 키 중복(`build.js:205`, `validate.js:566`)만 찾는다. R17 은 `44-weapon-art.js` 의 자유변수만 본다. 내가 `src/*.js` 를 modules.json 순서로 훑어 만든 임시 스크립트(들여쓰기 0~2 의 `function`/`const`/`let`/`var`)는 **현재 충돌 0건, 최상위 이름 1688개**를 냈다.
**무엇이 문제인가**: 지금은 깨끗하다. 그러나 `function foo` 두 개나 `var` 중복은 같은 클로저에서 에러 없이 뒤쪽이 이긴다. `const` 중복은 SyntaxError 로 시끄럽게 죽으니 괜찮다. 1688개 이름과 54개 모듈에서 "조용히 깨지는" 부류가 남는다. CLAUDE.md 가 이미 "한 번 이것 때문에" 사고를 겪었다고 적었다.
**언제 터지는가**: 병렬 worktree 로 기능을 동시에 추가하는 다음 묶음. 서로 모르는 두 브랜치가 `render`, `update` 같은 이름을 하나씩 넣고 병합한다.
**제안**: `validate.js` 에 21번째 규칙으로 위 스크립트를 넣는다(modules.json 순서대로 최상위 선언 이름을 모아 중복이면 두 파일을 지목해 실패). 정규식 기반이라 `build.js` 와 같은 정적 방식이다.
**반대 심문**: 정규식은 들여쓰기에 의존해 놓치는 선언이 있을 수 있다(예: 구조 분해 `const {a, b} =`). 완전한 검사는 아니다. 그래도 지금 0건이므로 새 위반을 막는 용도로는 충분하다.

### 4. 락파일이 없어 CI 가 날짜에 따라 다른 Chrome 을 받는다 — 심각도 하 · 비용 소
**증거**: `ls package-lock.json` 없음. `package.json`: `"puppeteer": "^25.4.0"`. `ci.yml` 캐시 키는 `hashFiles('package.json')` 이고 설치는 `npm install`. `docs/RELEASING.md` "앞으로 할 일: `npm install --package-lock-only` 를 돌려 커밋". 이 머신의 puppeteer 는 25.4.0 (npx 캐시).
**무엇이 문제인가**: 캐시가 빗나가는 날(7일 미사용, 키 변경) 25.x 중 최신과 그에 맞는 Chrome for Testing 이 내려온다. 이 스위트는 프레임 타이밍에 민감하고(CLAUDE.md 의 프레임 기아) 스위트 C 는 puppeteer ≥ 25 의 확장 기능을 쓴다. 코드가 같아도 브라우저가 바뀌어 어느 날 빨개질 수 있다.
**언제 터지는가**: 출시 후 몇 달 안, 아무 커밋도 없는 날에 push 한 CI 에서. 릴리스 태그 푸시(`release.yml`)가 그 날이면 릴리스가 막힌다.
**제안**: 이미 RELEASING.md 가 적은 대로 네트워크가 되는 곳에서 `npm install --package-lock-only` 로 락파일을 커밋하고 `npm ci` + `setup-node cache: npm` 으로 되돌린다. 설명으로 든 이유("락파일 없이는 npm ci 가 안 됨")는 락파일을 만들면 사라진다.
**반대 심문**: 캐럿은 25.x 에만 걸리고 puppeteer 는 마이너에서 Chrome 을 자주 올리지만 호환 깨짐은 드물다. 영향은 CI 에 한정되고 사용자 배포물은 puppeteer 와 무관하다. 그래서 심각도 하다.

### 5. 문서만 바꾼 푸시는 CI 를 건너뛰어 생성물 어긋남이 새어 들어갈 수 있다 — 심각도 하 · 비용 소
**증거**: `.github/workflows/ci.yml` 의 `paths-ignore` 가 `docs/**` 와 `**/*.md` 를 제외한다. `docs/BALANCE.md` 는 생성물이고 검사는 `balance.js --check` 안에 있다(`tools/balance.js:1064` 부근, `options/arsenal.json` 도 같은 곳에서 검사).
**무엇이 문제인가**: `docs/BALANCE.md` 를 손으로 고친 커밋은 CI 가 돌지 않아 어긋남이 통과한다. 다음 코드 푸시에서 비로소 실패해 원인 커밋을 찾기 어렵다. (질문 3 의 `arsenal.json` 은 **문제 없음**: `options/arsenal.json` 은 `balance.js --write` 가 만들고 `--check` 가 낡음을 잡으며 CI 가 `src/` 변경 때 돈다.)
**언제 터지는가**: 누군가(혼자라도 미래의 나) 표를 손으로 보정할 때.
**제안**: `paths-ignore` 에서 `docs/BALANCE.md` 만 빼거나 `!docs/BALANCE.md` 를 추가한다.
**반대 심문**: CLAUDE.md 가 "손으로 고치지 않는다"고 명시하고 PR 체크리스트에도 있다. 사고 확률이 낮다.

### 6. 외부 창구는 갖췄지만 출시 필수 문서 두 개가 비어 있다 — 심각도 하 · 비용 소
**증거**: `CONTRIBUTING.md` 250줄, PR 템플릿 31줄(금지 API·`data-crs`·로케일 체크리스트까지 실용적), 이슈 템플릿 3종(`bug_report.yml` 107줄, `blank_issues_enabled: false`). 그러나 `ls SECURITY.md CODE_OF_CONDUCT.md` 는 둘 다 없음. `config.yml` 은 비공개 보안 권고 URL 로 보내지만 저장소에서 그 기능이 켜져 있는지는 파일로 확인할 수 없다.
**무엇이 문제인가**: 창구 자체는 충분하다. 비어 있는 것은 보안 신고 안내문과 웹스토어 심사가 요구하는 개인정보 처리방침/지원 URL 쪽이다(후자는 이 저장소에서 찾지 못했다. 스토어 콘솔 쪽 설정일 수 있어 확정하지 않는다).
**언제 터지는가**: 스토어 제출 때 또는 첫 취약점 제보 때.
**제안**: SECURITY.md 한 장(신고 경로, 지원 버전)과 개인정보 문구 한 단락. 코드 변경 없음.
**반대 심문**: 1인 프로젝트에서 CoC 는 과하다. 스토어는 처리방침을 콘솔에 직접 붙여 넣을 수도 있다.

## 확인 못 한 것
- `ammo`/`rules`/`core` 이후 블록 시간과 스위트 B·C·D 시간. 부하가 높고 워치독이 걸려 측정하지 못했다(위 추정값은 `test/e2e.js` 주석).
- 실제 Chrome 에서의 실행(초기화 포함) 시간과 느린 기기 체감. Node 컴파일 7 ms 만 측정했다.
- `content.js` 가 1.19MB 에서 예산 1600KB 까지 가는 데 걸리는 정확한 기간(최근 3주 평탄이라는 사실만 측정).
- GitHub 쪽 설정(Discussions, 비공개 보안 권고, 브랜치 보호)과 스토어 콘솔 설정.
- 질문 5 의 검사는 내 임시 정규식이다. 구조 분해 선언 등 일부는 놓칠 수 있다.
- `publish-store.yml` 의 실제 배포 경로는 읽기만 했고 시크릿 구성은 확인할 수 없다.
