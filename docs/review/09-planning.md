# 축 10 — 기획 관점 (범위 · 순서 · 성공 기준)

## 요약 (3줄)

기획 단위 36개 중 **16개(44%)가 사용자 인용 없이 추가**됐고, 그중 10단계의 아홉 기능은 전부
`docs/specs/product.md` 에 인용이 한 줄도 없는 채로 들어와 **기본 경로에서 하나도 보이지 않는다.**
순서의 진짜 결함은 "1단계 끝나고 안 냈다"가 아니다 — 작업일은 6일뿐이라 조기 출시의 되먹임이
빌드보다 느렸다. 결함은 **2026-10-15 에 v2.0.0 릴리스를 7단계까지 밟아 놓고 태그를 안 붙인 것**이고,
그 때문에 버전 경계가 사라져 **그 뒤 39커밋이 CHANGELOG 에 한 줄도 안 남았다.**
성공 기준은 10편 중 2편에만 있다. 나머지는 전부 "테스트 통과"이고, 그래서 **제품이 성공했는지
물어본 적이 없다.**

## 유지할 것 (3줄)

1. **명세를 구현 전에 쓰고 버전 관리에 넣은 것.** `docs/specs/README.md:6-8` 이 그 교훈("임시
   디렉터리에서 열흘 만에 사라졌다")을 문서 안에 박아 뒀다. 10편 전부가 구현 커밋보다 앞선다.
2. **인용을 명세 머리에 박는 관습.** `material.md:6`, `combat.md:52`, `weapon-identity.md:3` —
   "왜 이걸 하는가"가 1차 자료로 남아 있어 이 리뷰의 출처 분해가 가능했다.
3. **`test-speed.md:149` 의 완료 기준 표** — 목표와 결과를 나란히 두고 미달 항목(`combat` 86초)을
   숨기지 않고 "지금은 남겨둔다"로 적었다. 열 편 중 유일하게 **단계가 자기 기준으로 실패할 수 있는** 형식이다.

## 성공 기준 제안 (측정 가능한 것 5개)

지금은 없다. `docs/ROADMAP.md:4` 가 "각 단계는 전체 테스트를 통과시키고 커밋해 푸시한 뒤 다음으로
넘어간다"로 완료를 정의하고, 명세 10편 중 **완료 기준 절이 있는 것은 4편**(settings §4,
test-speed §9, product §8, weapon-identity §E)뿐이며 그중 **제품 결과를 숫자로 적은 것은 2편**이다.

목표가 "개인 재미 + 스토어 출시"이므로 넷은 텔레메트리 0, 하나는 유통 채널이 그냥 주는 숫자다.

| # | 기준 | 어떻게 재나 | 비용 |
|---|---|---|---|
| S1 | **공개돼 있다.** 스토어에 게시되어 있고 90일 뒤 설치 ≥ 30, 리뷰 ≥ 3 | 개발자 대시보드. 확장에 코드 한 줄 안 넣는다 | 소 |
| S2 | **본인이 계속 쓴다.** `crsStats` 의 "최근 7일 사용 일수" ≥ 3 | **이미 구현됨** — `docs/specs/product.md:31` | 0 |
| S3 | **닫기보다 되돌리기가 많다.** 복구 비율 `복구/(복구+종료)` ≥ 50% | **이미 구현됨** — `product.md:31` | 0 |
| S4 | **무기고가 목록이 아니다.** 30일 뒤 사용 하위 8종의 합이 전체 사격의 10% 미만이면 **밸런스가 아니라 범위 문제**로 판정 | `crsStats` 에 무기별 사격 수 한 필드 추가 | 소 |

S3 과 S4 가 핵심이다. S3 은 "재미있었나"의 가장 싼 대리값이고, S4 는 이 프로젝트가 한 달을
더 잘못 갈 수 있는 유일한 방향(무기 추가)에 처음으로 숫자를 붙인다.

## 발견 (심각도 순)

### 1. v2.0.0 을 체크리스트 7번까지 밟고 태그를 안 붙였다 — 그래서 변경 기록이 멈췄다 — 심각도 상 · 비용 소

**증거**
- `git tag -l` → **0개**. 커밋 `7a5dfa5 chore(release): v2.0.0 — 로드맵 열 단계 완료` (2026-10-15)
  가 `manifest.json` / `package.json` / `src/00-prelude.js` 세 곳을 2.0.0 으로 올리고
  `CHANGELOG.md:171` 의 `## [2.0.0] - 2026-10-15` 절을 썼다.
- `docs/RELEASING.md:356-369` 의 14항 체크리스트에서 8번이 `git commit / git tag v<버전>`,
  10번이 `git push origin v<버전>` 이다. **남은 일은 명령 두 줄이었다.**
  `.github/workflows/release.yml:5-7` 은 `v*` 태그를 기다리고 있고 2026-10-02(`cb11c0c`)부터 그 자리에 있었다.
- `CHANGELOG.md` 의 마지막 수정 커밋이 바로 그 `7a5dfa5` 다. **그 뒤 39커밋(11·12단계 전부)이
  CHANGELOG 에 한 줄도 없다.** `CHANGELOG.md:11` 의 `[Unreleased]` 는 지금도 **2.0.0 이전** 내용
  (4~7단계)을 담고 있어 `[2.0.0]` 절과 중복이다. `docs/RELEASING.md:75` 가 "`[Unreleased]` 는 빈
  상태로 남깁니다"라고 못박았는데 안 비웠다.
- `tools/validate.js:668` 의 R14 는 "현재 매니페스트 버전의 절이 존재하는가"만 본다. 2.0.0 절이
  있으므로 **통과한다.** 낡은 `[Unreleased]` 도 11·12단계 누락도 못 잡는다.

**무엇이 문제인가**
출시를 안 한 비용은 "피드백을 못 받았다"가 아니다(§2 반대 심문 참조). 비용은 **버전 경계가
사라진 것**이다. 11단계는 미니건 명중률을 4% → 68% 로 바꾸고 23종 전부의 표적 등급 계수를 새로
넣었다(`ROADMAP.md:178-184`). 12단계는 HUD 안내 문구를 바꿨다(`ROADMAP.md:210`). 이건 전부
사용자가 보는 동작 변경인데 **버전은 2.0.0 그대로**고 기록은 0줄이다. 태그가 붙었다면 다음 묶음은
v2.1.0 이 됐을 것이고, R14 가 "2.1.0 절이 없다"로 **반드시 실패했을 것이다.** 태그를 안 붙인
선택이 저장소의 유일한 강제 장치를 껐다.

**재미 또는 출시 중 무엇을 해치는가**
출시. 스토어에 올리는 순간 "이 버전이 뭐가 달라졌나"를 적어야 하고, 지금 그 답은 10-15 에서 멈춰 있다.
되돌리기도 막힌다 — `docs/RELEASING.md:344` 가 "스토어는 이전 버전으로 되돌릴 수 없다"고 적는데,
어느 커밋이 어느 버전인지 표시가 없으면 되돌릴 대상도 못 고른다.

**제안**
`7a5dfa5` 에 `v2.0.0` 을 소급해 태그하고, 11·12단계를 `## [2.1.0]` 로 묶어 CHANGELOG 에 쓴 뒤
버전을 2.1.0 으로 올려 태그한다. 그리고 R14 를 넓혀 (a) `[Unreleased]` 가 비지 않은 채 태그 버전이
올라가면 실패, (b) `git describe` 로 본 마지막 태그 이후 커밋이 N개를 넘으면 경고하게 한다.
`release.yml` 과 `publish-store.yml` 은 이미 있으므로 추가 인프라는 없다.

**반대 심문**
"혼자 쓰는 것이면 태그가 왜 필요한가" — 이 반론은 목표가 개인 재미뿐일 때만 성립한다. 사용자가
스토어 출시를 확정했으므로 안 성립한다. 더 센 반론: "11·12단계가 끝나고 한 번에 2.1.0 으로
태그하면 되지 않나" — 그렇다. 그런데 **11·12단계는 2026-11-04 에 끝났고 오늘은 11-12 다.**
8일이 더 지났고 여전히 태그도 CHANGELOG 항목도 없다. "끝나면 한다"가 실제로 작동하지 않았다는
것이 증거로 남아 있다.

### 2. 인용 없이 추가된 10단계 아홉 기능이 기본 경로에서 하나도 안 보인다 — 심각도 상 · 비용 중

**증거**
- `docs/specs/product.md` 101줄 전체에 사용자 인용 0건. 다른 명세 아홉 편에는 전부 있다.
- `settings-schema.json:2` `mode` 기본값 `rampage` → **적이 없다.** 보스전은 전투 모드 안에서만
  승격하므로(`product.md:50`) 기본 경로에서 영영 안 뜬다.
- `settings-schema.json:26` `unlockAll` 기본값 **`true`**. `product.md:54` 가 스스로 적는다 —
  "기본 설정 `unlockAll: true` 라 아무도 막히지 않는다." **해금 임계 8개(기관총 5k … 붕괴 500k)를
  명세하고 구현하고 테스트해 놓고 기본값으로 꺼 뒀다.**
- 챌린지 `C` · 인스펙터 `I` · 공유 `P` 는 `src/95-events.js:169-171` 의 키보드 전용이다.
  `src/45-hud.js` 에 진입 버튼이 없고, 챌린지 진행 행은 챌린지가 **이미 돌 때만** 그려진다(`45-hud.js:370`).
- `recordReplay` 기본값 `true`(`settings-schema.json:27`) 지만 재생 수단은 옵션 페이지 안에 있다.
- 결과: **툴바 아이콘을 눌러 켠 직후 화면에서 10단계 기능은 0개가 보인다.**

**무엇이 문제인가**
10단계는 "제품화"라는 이름이 붙은 단계인데, 그 안의 아홉 기능 중 **낯선 사람이 우연히 만날 수 있는
것이 하나도 없다.** 본인은 전부 알고 있으니 기본값을 바꿀 이유가 없었고 — 이게 혼자 만들 때의
전형적인 맹점이다. 특히 해금은 이 제품의 **유일한 진행 구조**인데 기본값으로 꺼져 있다.
개인 재미로 보면 합리적인 선택(다 쓰고 싶다)이고 출시로 보면 자해다.

**재미 또는 출시 중 무엇을 해치는가**
양쪽. 출시: 만든 것의 대부분이 전달되지 않는다. 재미: 23종 무기와 해금을 만들어 놓고 본인조차
`rampage` 기본값으로 켜면 적도 진행도 없는 화면에서 시작한다.

**제안**
코드를 고치지 말고 **기본값 두 개만 결정**한다 — `unlockAll: false`(스토어판), 그리고 첫 실행
모드를 `arcade` 로 둘지. 그리고 10단계 아홉 기능을 **"기본 노출" / "고급 뒤"** 두 통으로 나누는
결정을 문서로 남긴다. 인스펙터·리플레이·사용자 정의 무기는 고급 쪽이 맞다(§7 참조).
HUD 진입점 추가 여부는 HUD 레인의 판단이므로 여기서는 **기본값 결정만** 제안한다.

**반대 심문**

드러났다(`ROADMAP.md:181-184`). 10단계까지는 그 측정이 없어서 못 봤다.

**재미 또는 출시 중 무엇을 해치는가**
양쪽. 11단계가 증명했듯 **제품 기준이 없으면 테스트가 전부 초록인 채로 재미가 망가진다.**

**무엇이 문제인가**
전부 같은 실패다 — **새 항목은 끝에 붙이고, 그 항목을 요약하는 머리말은 안 고친다.** 혼자 작업할
때는 비용이 0이다(머릿속에 최신이 있으니까). 그런데 `docs/specs/README.md:3` 이 스스로 적듯 명세는
"**구현 에이전트가 읽는 1차 자료**" 다. 다음 작업자(에이전트든 6개월 뒤의 본인이든)가 색인을 믿으면
"combat 은 진행 중이고 weapon-identity 라는 명세는 없다"로 읽는다.

**재미 또는 출시 중 무엇을 해치는가**
둘 다 직접은 아니다. 다음 작업의 정확도를 해친다. 그리고 발견 1·4 와 같은 뿌리이므로 여기만
고쳐서는 재발한다.

**제안**
다섯 군데(`ROADMAP.md:7-18`, `specs/README.md:10-21`, `CLAUDE.md:22`·`:78`, `CONTRIBUTING.md:178`,
`README.md` 기능 목록)를 한 번에 맞춘다. 재발 방지는 숫자를 문서에서 빼는 쪽이 싸다 —
단언 수·규칙 수·초는 **도구가 출력하는 값**이므로 문서에는 "수치는 `node tools/validate.js` /
`node test/e2e.js` 의 출력을 본다"로 적고 숫자를 지운다. 상태표는 `specs/README.md` 에서 없애고
ROADMAP 의 단계 표시 하나만 정본으로 둔다(**지금 두 곳이 같은 상태를 다르게 말하고 있다**).

**반대 심문**
"문서 정확도는 factcheck 레인 일이다" — 이 항목이 다루는 것은 문서의 사실 여부가 아니라
**정본이 두 곳에 있어서 갈라졌다는 기획 구조 문제**(`ROADMAP` 단계 표시 ↔ `specs/README` 상태표)다.
단순 오타 교정은 저쪽 레인에 맡긴다. 더 센 반론: "ROADMAP:9 머리말은 10단계 시점의 스냅샷으로
읽으면 틀린 게 아니다" — `## 현재 상태` 라는 제목이 그 해석을 막는다.

2. **2~4단계를 이끈 피드백은 1단계가 끝나기 전에 이미 손에 있었다.** `combat.md`(적만 피해 ·

## 확인 못 한 것

- **피드백 제공자가 몇 명인가.** 인용 17개가 전부 같은 어투이고 저장소 전체에 "사용자들" 복수형이
  0회, git 저자가 사실상 1명(이충현)이지만, **인용의 출처가 본인인지 제3자인지는 확인할 수 없었다.**
  §6 의 "측정이 없다"는 진단은 제공자 수와 무관하게 성립한다.
- **GitHub 쪽 상태** — 이슈·PR·Actions 실행 이력·릴리스 페이지는 확인하지 않았다. 로컬 저장소에
  태그가 0개라는 것만 확인했다. 원격에 태그가 있을 가능성은 낮지만 배제하지 못했다.
- **스토어 등록 여부** — 저장소에 스토어 ID·스크린샷·프로모 자산이 없고 `publish-store.yml` 이
  수동 실행 전용이라는 것만 확인했다. 실제 대시보드에 초안이 있는지는 모른다.
- **`crsStats` 의 실제 값.** 본인 브라우저에만 있으므로 복구 비율·사용 일수의 현재 수치를 못 봤다.
  S2·S3 은 **이미 구현된 지표를 읽자**는 제안이지 새로 만들자는 제안이 아니다.
- **옵션 페이지가 10단계 기능을 실제로 얼마나 노출하는지** — `options/options.js` 1202줄을
  끝까지 읽지 않았다. 발견 2 는 **기본값과 진입 키 바인딩**만 근거로 한다.
