# 테스트 속도

2단계(설정) 병합 직후, 3단계 시작 전에 적용한다. 남은 일곱 단계가 전부 혜택을 본다.

## 1. 측정

| | 전 | 후 |
|---|---|---|
| 단언 수 | 559 | **605** (본문 545 동일 + 블록별 증거 집계 8) |
| 전체 실행 시간 | 179초 | **86초** |
| 고정 대기 합계 | 91초 | 58초 |
| `sleep()` 호출 | 258회 | 250회 |
| 가장 긴 것 | 10초 하나 | 2.8초 |
| 블록 단독 실행 | 없음 | `settings` 5.5초 · `ammo` 41초 · `core` 49초 · `combat` 86초 |

에이전트는 검증 과정에서 이걸 5~10번 돌린다. 전체 실행이 180초를 넘으면 도구 호출 없이
180초가 지나 에이전트가 죽는다 — 실제로 다섯 번 그렇게 죽었다. 86초면 그 한계의 절반이고,
건드린 블록만 돌리면 5~49초다.

남은 긴 쪽은 `combat`(86초)이고 전체 실행 시간은 이제 그 한 레인이 정한다. 더 줄이려면
`combat` 을 §7 / §9.4 / §10.6 세 블록으로 다시 쪼갠다. 지금 당장은 필요 없다.

## 2. 왜 폴링으로 못 줄이는가

긴 대기의 대부분은 **"기다렸는데 아무 일도 안 일어났다"를 증명하는 부정 단언**이다.

- 10초: 수명 무제한 설정에서 조각이 사라지지 않는지
- 3.5초: 피한 플레이어를 탄환이 못 맞히고 소멸하는지
- 1.7초 ×5: 1.5초 복구 빔이 끝나는지
- 2.82초: 3.0초 락온이 아직 발사되지 않았는지

폴링은 조건이 **참이 되기를** 기다릴 때만 빠르다. 조건이 끝까지 거짓임을 보이려면 그 시간을
다 기다려야 한다. 줄이려면 **제품의 시간 상수 자체를 줄이는 수밖에 없다.**

## 3. `debug.timeScale`

`later(fn, ms)` 가 76개 타이머의 단일 통로다. 여기에 배율을 넣는다.

```js
const debug = { …, timeScale: 1 };
function dur(ms) { return ms * clamp(debug.timeScale, 0.05, 1); }
function later(fn, ms) { … setT(…, dur(ms)) … }
```

- 범위 `[0.05, 1]`. **느리게는 못 만든다.** 테스트가 제품을 느리게 만들어 가려는 일을 막는다.
- `later()` 만으로는 부족하다. 타임스탬프를 지속 시간과 비교하는 곳도 `dur()` 을 거치게 한다:
  파편 수명, 락온 3단계, 복구 빔 1.5초, 전투 유예, 공회전 유예, 과열 냉각, 연소 틱.
  대상은 "경과 시간 >= 상수" 형태의 비교 전부다.
- **WAAPI 애니메이션은 배율을 받지 않는다.** 57곳이고 대부분 연출이라 테스트가 기다리지 않는다.
  애니메이션 완료를 기다리는 단언은 배율 1 로 남긴다.

## 4. 테스트에서의 사용 규칙

- 기본값은 **1** 이다. 배율은 테스트가 명시적으로 켠다.
- **타이밍 자체를 검증하는 단언은 배율 1 로 돌린다.** 락온 3단계의 각 구간 길이, 공회전 유예
  0.6초, 과열 2.5초처럼 "그 시간이 맞는가"가 요점인 것들이다. 이걸 배율로 돌리면 검증이 사라진다.
- **결과만 보는 단언은 0.25 로 돌린다.** "락온이 끝나면 피해를 받는다", "복구 빔이 끝나면
  요소가 되살아난다", "수명이 다하면 조각이 사라진다" 같은 것들이다.
- 블록 진입 시 설정하고 나갈 때 1 로 되돌린다. 남겨두면 다음 블록이 조용히 빨라진다.

예상 절감: 1.5초 이상 대기 50.5초 중 타이밍 검증용을 뺀 약 40초가 10초로 줄어든다.
전체 200초 → **약 160초**.

## 5. 블록 단위 분할

스위트 A 가 긴 쪽이다. 이름 있는 블록으로 쪼개고 환경변수로 고른다.

```
CRS_BLOCKS=settings node test/e2e.js
CRS_BLOCKS=core,ammo node test/e2e.js
```

블록은 **실제로 분리 가능한 이음매**에서 자른다. 일곱이다.

| 블록 | 시간 | 내용 |
|---|---|---|
| `core` | 56초 | 픽스처·주입·활성화·HP·무기 파워·v1.5 무기 아트·재질 |
| `ammo` | 42초 | 탄창·재장전·저격경·로드아웃·적·KO·종료, 가독성 |
| `combat` | 35초 | 드론·락온·복구 (§7) |
| `debris` | 30초 | 파편 수명 (§9.4) |
| `depth` | 24초 | 깊이·관통 (§10.6) |
| `rules` | 19초 | 모드·적만 피해·적만 포커싱 (§A/§B/§D1) |
| `settings` | 6초 | 스키마·저장소·성능 가드·접근성 |

처음엔 넷이었다. 3단계가 전투 쪽에 단언을 얹으면서 `combat` 이 100초가 되어 혼자 전체
실행 시간을 정하게 됐고, 그 안의 네 구획이 상태를 공유한 적이 없다는 것 — 저마다 모드와
디버그 플래그와 장면을 진입에서 새로 만든다 — 이 드러나서 탭만 공유하고 있었을 뿐이라
그대로 넷으로 갈랐다. 전체 101초 → **57초**.

`core` 안쪽은 2,000줄짜리 단일 스코프라 더 쪼개려면 블록마다 선언된 `const` 를 전부
끌어내야 한다. 지금은 회귀 위험이 이득보다 크다. 전체 실행 시간이 다시 문제가 되면
그때가 `core` 를 함수로 분해할 때다.

### 5.1 각 블록은 자기 전제를 스스로 만든다

블록은 저마다 **자기 브라우저와 자기 페이지**를 연다. `freshPage()` 가 공통 전제를 만든다:
픽스처 로드, USER 오리진 CSS 주입, 타이머 원장, 크롬 심, content.js 활성화, 그리고 정확
피해 단언이 전제하는 디버그 플래그.

- `content.js` 는 **토글**이다. 활성 페이지에서 다시 평가하면 꺼진다. 스스로 활성화하며
  그 반환값을 단언하는 블록(`combat`)은 `{ activate: false }` 로 페이지를 받는다.
- 블록은 자기 페이지의 콘솔·CSP·`lastError` 증거를 **스스로** 집계한다(`closeBlockPage()`).
  스위트 전체에 하나뿐이던 집계는 페이지가 하나일 때만 성립했다.

### 5.2 동시 실행

블록들과 스위트 B, C 가 각자 브라우저를 들고 **동시에** 돈다. 벽시계는 합이 아니라
가장 느린 한 레인과 동시 실행 수가 함께 정한다. 레인이 슬롯보다 많으므로 **긴 레인을
먼저 큐에 넣는다** — 57초짜리가 마지막에 서면 그 길이가 통째로 더해진다.

**천장은 코어 수가 아니라 프레임 기아다.** 12코어에서 6레인이 가장 빨랐고(59초 대 84초),
그 숫자는 다음 단계를 넘기지 못했다. 단언이 797개에서 826개가 되고 타격당 렌더링이
무거워지자 6레인은 3회 중 3회 졌고, 같은 부하에서 main 은 3회 중 3회 통과했다.
지는 단언은 **페이지가 실제로 프레임을 받아야 하는 것들**이다 — 450ms 키 입력에 드론이
아예 안 움직이고, 뷰모델 스윙이 정점 아래에서 잡히고, 600ms 예산을 17ms 넘긴다.
측정이 틀린 게 아니라 제품이 굶는 것이고, 스위트가 커질 때마다 돌아온다.

기본값은 `min(4, 코어 수 - 1)` 이다. 4코어 CI 러너는 3이 된다. **스위트가 커지면
다시 재서 정한다 — 추측하지 않는다.** `CRS_LANES=1` 로 완전 직렬화할 수 있다.

### 5.3 규칙

- 부분 실행은 요약에 `*** PARTIAL RUN ***` 을 찍고 총 실행 시간 단언을 건너뛴다.
- 모르는 블록 이름은 **즉시 종료**다. 오타가 "0개 블록 통과"로 초록이 되면 안 된다.
- **완료 판정은 항상 전체 실행이다.** 블록 선택은 반복용이다.

## 6. 왕복 줄이기

`page.evaluate` 242회에 단언 560개다. 한 번의 평가에서 여러 값을 한꺼번에 읽는 쪽으로
새 단언을 쓴다. 기존 것을 전부 고치지는 않는다 — 비용 대비 효과가 낮고 회귀 위험이 있다.
**새로 쓰는 단언에만 적용하는 규칙**으로 둔다.

## 7. 하지 않는 것

- 단언을 지우지 않는다. 느리다고 검증을 버리는 건 거래가 아니다.
- 스위트 B(엄격 CSP)와 C(실제 확장 로드)를 줄이지 않는다. 각각 한 번씩만 돌고
  다른 데서 못 잡는 것을 잡는다.
- 제품 코드를 테스트 편의로 바꾸지 않는다. `timeScale` 은 디버그 훅이고 기본값이 1 이다.

## 8. 테스트

1. `debug.timeScale = 0.25` 에서 3.0초 락온이 0.75초 ±0.1 에 해결된다.
2. `timeScale` 이 `[0.05, 1]` 로 클램프된다. 2 를 넣으면 1 이 된다.
3. 배율이 켜진 채 `restore()`/`deactivate()` 해도 타이머가 남지 않는다.
4. `CRS_BLOCKS=core` 가 core 블록만 돌리고 요약에 부분 실행이라고 찍는다.
5. 각 블록을 **단독으로** 돌려도 통과한다(블록 간 결합 없음). 아홉 블록을 각각 한 번씩 돌린다.
6. 전체 실행의 단언 수가 블록 단독 실행들의 합과 같다.

## 9. 완료 기준 ✅ 달성

| 기준 | 목표 | 결과 |
|---|---|---|
| 전체 실행 시간 | 160초 이하 | **86.0초** |
| 블록 단독 실행 | 60초 이하 | `core` 49초 · `ammo` 41초 · `settings` 5.5초 · **`combat` 86초** |
| 단언 수 | 줄지 않는다 | 본문 545 → 545, 총 597 → 605 |
| 전체 스위트 | 통과 | 605 통과 / 0 실패 |

`combat` 만 60초 기준을 넘는다. 그 블록은 고정 대기가 본질인 단언(3.0초 락온, 1.5초 복구 빔,
파편 수명)이 모여 있는 곳이라 §7 / §9.4 / §10.6 으로 다시 쪼개는 것 말고는 줄일 방법이 없다.
전체 실행이 목표의 절반이므로 지금은 남겨둔다.
