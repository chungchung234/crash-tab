# 이 머신에서 테스트를 돌리는 법 (반드시 지킬 것)

이 머신은 다른 작업으로 상시 부하가 높다(12코어에 평균 15~29). 백신이 CPU 의 50% 가까이
쓰고 있어 Chrome 이 임시 파일을 쓸 때마다 검사가 걸린다.

측정값:
- 전체 스위트: 한가할 때 203초 → 지금 400초 이상
- 스위트 A 만: 한가할 때 67초 → 지금 **121초**

## 절대 규칙

**테스트나 빌드처럼 2분을 넘길 수 있는 명령은 반드시 `run_in_background: true` 로 돌리고
출력 파일을 폴링한다.** 포그라운드로 돌리면 결과를 기다리는 동안 도구 호출이 멈추고,
3분 무진행이면 에이전트가 정지로 판정되어 죽는다. 이 세션에서 이미 세 번 그렇게 잃었다.

올바른 형태:

1. `node test/e2e.js > /tmp/<이름>.log 2>&1` 를 `run_in_background: true` 로 시작한다.
2. 돌아온 출력 파일 경로나 `/tmp/<이름>.log` 를 20~30초 간격으로 `tail` 해서 진행을 확인한다.
   폴링 자체가 도구 호출이므로 정지 판정을 피한다.
3. `SUMMARY:` 줄이 보이면 끝난 것이다.

## 반복 중에는 스위트 A 만

`CRS_SUITES=A node test/e2e.js` — 121초. 전체는 완료 판정 때 한 번만 돌린다.

## 시간 예산

`CRS_TIME_BUDGET_MS=900000` 을 항상 붙인다. 기본값 240초는 이 부하에서 전체 스위트를 중간에
끊는다. 이 값은 테스트 안의 "총 실행 시간" 단언에만 쓰이며 커밋하지 않는다.

## 부하로 인한 가짜 실패

부하가 높을 때 다음이 간헐적으로 난다. 코드 회귀가 아니다. 한가할 때 다시 돌려 확인한다.
- `Attempted to use detached Frame` — 프레임이 평가 도중 분리됨
- 물리 안정화를 기다리는 단언(파편 정지, 재낙하)이 경합에서 짐
- `total runtime < N s` 단언

같은 실패가 한가한 상태에서도 재현되어야 진짜 결함이다.
